# Cancellation financial closure — sandbox 0049

Finance can explicitly complete an operationally cancelled, approved request when its recorded payment is failed and a retained staff gateway inquiry confirms rejection at the current payment version. A browser cancellation alone, missing history, pending/unknown result, successful payment, paid receipt, stale versions or incomplete cancellation never qualify. No gateway request runs inside the closure transaction.

`GET /api/v1/admin/order-requests/{id}/financial-closure-plan` exposes current order/request/payment versions, inquiry identity and eligibility. Closure history and actor-owned receipt recovery use `financial-closures` and `financial-closures/{key}`. Reads require both payments.read and orders.read_all. Writes independently recheck finance.write, payments.read and orders.read_all under the existing account lock, then the shared fulfillment lock and payment→order→request locks. Commands bind versions, the exact inquiry, a stable operation ID and a reason.

The command completes the request, advances order/request versions, retains an immutable receipt, records audit/notification/outbox and marks the active closure on order state, atomically. It does not alter payment status, stock, costs, coupon history, cash/bank balances or create a refund. Same-command retry returns its original receipt, including after later financial activity. Existing histories remain untouched; migration 0049 adds only the retained closure table, with one closure per request/inquiry pair. No historical value is invented.

Any later authoritative verification that reports success **or uncertainty** reopens the associated completed request for financial review, removes the active closure marker, and records a separate system audit/notification/event. Its previous closure receipt stays unchanged. Successful late payment creates the original paid receipt and eligibility for the existing explicitly simulated refund workflow; the cancelled order never reacquires stock or returns to fulfillment. Unknown remains verification, never failed. A new confirmed rejected inquiry may then be reviewed and closed again. Paid callback replay cannot erase refunds or reopen completed refunded requests.

The existing Persian/English request screen presents finance closure separately from cancellation, with shared controls, retained reasons, version conflicts, unknown-result receipt recovery, session cache clearing, and a combined navigation guard for cancellation/finance drafts. Staff can reach the order's existing payment workspace for inquiry. A closure receipt is historical evidence; current payment/order status remains authoritative. Customer request status and owned notifications distinguish no-payment closure from money returned.

Database-backed tests cover explicit rejection, unavailable/stale inquiry evidence, no-money/no-stock effects, immutable retries, rollback, independent finance permission, late success→refund→callback replay, unknown reopening→new rejected inquiry→second closure, and outbox consumption once. Browser verification uses **new isolated demo records with clearly labeled synthetic imported rejection evidence**, not a real provider transaction; gateway verification behavior is tested using the sandbox adapter stub in database-backed tests.

Production activation and FUT features remain excluded.
