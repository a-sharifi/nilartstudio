# Production batches, WIP and quality control

Live sandbox workspace: `/fa/admin/production` and `/en/admin/production`. Batch details and QC use `/admin/production/:id` and `/admin/production/:id/qc`. Existing `/admin/inventory/production-orders`, `/admin/inventory/batches` and `/admin/inventory/quality` URLs open this workspace. `/admin/production/losses` lists recorded batches with normal waste, abnormal damaged output or WIP write-off.

## Workflow and records

1. Select an explicitly saved recipe revision, production date, batch number and positive target. Drafts retain SKU/BOM identities and version, material/service lines and planned base quantities. Missing consumption, waste/conversion configuration or an ineffective recipe prevents draft creation. Saved recipe revisions remain immutable; later recipe/rate changes do not reprice the batch.
2. Start the saved batch. Material issues consume only available stock at the recorded moving weighted average. Repeated BOM lines share their material's position. Every issue changes stock and recorded WIP atomically with the batch version, audit and outbox event. Production does not silently reserve planned material stock.
3. Return unused materials, bounded by net issued quantity per batch line. Return valuation preserves the outstanding issued cost, including the final rounding remainder, rather than using a later replacement rate or current warehouse average.
4. Record actual service totals explicitly in IRT, including explicit zero when appropriate. Revisions replace that line's actual total; they do not add it a second time. This records a production cost, not a supplier/artist obligation, payment or settlement. Unrecorded services remain null; recorded WIP totals only known costs and is labeled incomplete until actual consumption/service records are complete.
5. QC records healthy output, normal waste and abnormal damage independently of the original target. Normal waste is absorbed into eligible output cost. Abnormal loss is allocated as `recorded batch cost × abnormal units / (healthy + abnormal units)`, rounded half-up to six decimal places. Healthy output receives the remaining exact value. A batch with no healthy output must classify total loss as abnormal damage. Completing twice or retrying a completion does not duplicate finished goods or cost.
6. Cancel only an open batch. Return all unused materials first, or explicitly authorize write-off of remaining issued materials/WIP as abnormal loss. Known costs remain traceable; missing actual costs remain explicitly incomplete. Completed/cancelled batches cannot silently reopen or change.

Amounts and quantities remain exact decimal strings. Planned quantities are six-place estimates, not automatic issue commands. Stock movements retain source kind/document/event links; manual inventory reversals cannot bypass production controls. Each command binds actor, complete intent and expected batch version to a stable operation ID. Uncertain responses support exact recovery/replay; conflicting versions retain inputs for explicit latest-version review. All reads and writes require the independent `production.manage` permission, and writes recheck fresh session/permission, Origin and CSRF. Inventory history still separately requires `inventory.manage`.

## Verification and limits

Migration 0039 is additive after purchasing 0038. The generic document-owned stock writer is shared with purchasing, whose public API stays intact. Tests cover pinned versions, independent permissions, exact retries, no duplicate completion, shared material stock, rollback, original issued-cost returns, explicit service costs, normal/abnormal waste and cancellation write-off. The isolated real browser journey creates synthetic product/SKU/BOM and purchased material, issues and returns material through the production UI, records services, completes QC, deliberately drops the completion response and verifies recovery plus exactly one healthy stock transfer. Persian mobile and existing purchasing workflows are checked.

This is a production increment, not completion of the full admin release. Parent orders split across multiple batches, scheduling/reservations, material substitutions, rework/reopening corrections, detailed labor time tracking, approved waste thresholds, print-file consumption and full finance/obligation/reporting integration remain pending. Stock-only waste has a searchable register at `/admin/waste` and `/admin/inventory/waste`, including linked reversal status, inventory history and a permitted link to production losses. Stock waste commands use the existing inventory adjustment workflow. Zero-value physical write-offs remain visible in production losses. Formal accounting and external production/provider activation are excluded.

## Sandbox deployment evidence — 2026-10-18

Main schema is at 0039 with no synthetic production batches. Existing stock and purchase snapshots matched before/after restored-copy migration, and a private backup preceded activation. All nine main services are healthy. Guest production and waste APIs return 401 with no-store caching; Persian/English and legacy production routes respond successfully. Production-only users do not receive inventory-history actions requiring a separate inventory permission. Recovery retains the operation after network failures, invalid acknowledgments and ambiguous server errors; definite validation/conflict/permission errors remain distinguishable.

Regression results: 606 backend tests and 347 frontend tests pass, along with twenty-one affected stock/supplier/shared-table browser checks. The real demo test covers both dropped connections and server errors after committed QC, plus original purchasing and stock-waste workflows. Seed requests reuse their session token to avoid unnecessary refreshes; application request limits remain enabled.
